# ADR-0001：本地优先、无云同步的数据架构

- 状态：Accepted
- 日期：2026-10-13
- 相关文档：[技术方案](../specs/课程表APP技术方案.md)（第 3 章数据模型）、[README 隐私章节](../../README.md)、[docs/README](../README.md)
- 相关代码：`core/data/db/AppDatabase.kt`、`core/data/db/Entities.kt`、`core/data/db/Migrations.kt`、`core/data/prefs/SettingsStore.kt`、`core/data/BackupManager.kt`、`app/schemas/com.zhijian.schedule.core.data.db.AppDatabase/`

## Context

课程表应用的核心数据是「谁、什么时候、上什么课」，还牵着教务账号口令——属于典型的个人敏感信息。同类产品（超级课程表、WakeUp 等）普遍走账号体系 + 云端课表，代价是：

- 必须自建服务端与账号体系，附带备案、合规与长期运维成本；
- 用户要多承担一层「课表被上传」的顾虑；
- 教务账号口令一旦上云，泄露面从「单台设备」放大到「服务提供方」。

而这个项目是单人维护、没有服务端预算。同时，高校官方教务 App 已经承担了"权威数据源"的角色，用户对本类产品的真实刚需是**课表好看、看得准、提醒准**，而不是跨端同步。

## Decision

**不设账号体系、不做官方云同步；所有数据只落在设备本地。**

- 结构化数据（课程、周次位掩码、考试、成绩快照、导入快照）→ Room，代码在 `core/data/db/`，schema 导出在 `app/schemas/com.zhijian.schedule.core.data.db.AppDatabase/`（当前 v3）。
- 设置项（主题、镜像加速开关、脚本仓库地址等）→ DataStore Preferences，代码在 `core/data/prefs/SettingsStore.kt`。
- 换机 / 备份靠**用户主动**导出导入：全量 JSON（`core/data/BackupManager.kt`）+ 二维码互传（`feature/importer/qr`）。
- 教务账号口令默认不落盘（技术方案 4.6 的约定）；与学校服务器的通信只发生在用户设备与学校服务器之间，不经过任何第三方。
- 系统日历是唯一对外的"弱同步"通道：`core/calendar/` 把课表写进用户自己的系统日历，数据跟随用户已有的日历账号，而不是跟随本项目。
- 真正的多端同步排到路线图后段（README「后续路线」：v1.1 WebDAV、v2.0 账号云同步），且届时**优先选用户自带存储（WebDAV）而不是官方云**。

## Consequences

正面：

- 没有服务端 → 没有备案、没有运维、没有集中式数据泄露面；隐私政策可以直白写"不收集、不上传"（README 隐私章节）。
- 除教务抓取外的全部功能离线可用，冷启动不受网络影响。
- 数据模型只需处理单设备一致性，不需要写冲突合并逻辑——这是省下来的最大一块复杂度。

必须接受的代价：

- 换机等于手工搬数据，用户容易丢；已有的两个兜底入口（JSON 备份、二维码互传）就是为这个代价付的账。
- 教务自动同步这类"需要后台跑"的能力只能依赖 WorkManager 在本机跑，无法用服务端兜底。
- 将来真要做多端同步时，本地自增主键需要补全局 id 与更新时间戳，是一笔实打实的迁移成本。
- 跨设备分享只能靠二维码/备份文件，无法做"分享课表链接"这类玩法。

## 备选方案

1. **账号体系 + 自建云**：否。合规、备案与运维成本与项目规模完全不匹配，而且会立刻摧毁"不收集不上传"这个核心卖点。
2. **账号 + 第三方 BaaS（Supabase / Firebase 之类）**：否。等同于把用户课表交给第三方，隐私叙事的收益归零。
3. **纯文件存储、不要数据库**：否。周次用位掩码查询、考试与课程的多表关联、成绩按学期聚合，用 SQL 表达最直接，自研文件索引反而更容易出错。
4. **只做本地但加密 Room（SQLCipher）**：暂缓。设备本已全盘加密（Android 文件级加密），再加一层数据库加密会引入密钥管理问题，收益不明显；如未来存入口令原文再重新评估。
