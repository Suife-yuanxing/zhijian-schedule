# ADR-0004：更新下载采用「8 路并发分片 + 镜像源链」

- 状态：Accepted
- 日期：2026-10-15（2026-10-17 修订镜像开关默认值）
- 相关文档：[下载加速设计 v2](../specs/2026-10-15-update-download-acceleration-design.md)、[v1 设计](../specs/2026-10-15-in-app-update-download-design.md)、[实施计划](../plans/2026-10-15-update-download-acceleration.md)、[ADR-0003](0003-github-releases-self-distribution.md)
- 相关代码：`core/update/ApkDownloader.kt`、`core/update/ResumableDownload.kt`、`core/update/DownloadSourceSet.kt`、`core/update/UpdateStore.kt`、`core/update/UpdateChecker.kt`

## Context

[ADR-0003](0003-github-releases-self-distribution.md) 把分发渠道定在 GitHub Releases 之后，v1 的应用内下载在真机上跑通了，但随即暴露了体验问题：**下载太慢**。

设计文档里记录的实测（2026-10-15，本地网络 + 真机；PC 经 Clash 代理，`github.com` → `release-assets`）：

| 路径 | 单连接 | 4 并发 | 8 并发 |
| --- | --- | --- | --- |
| PC 经代理直连 release-assets | 82 KB/s | 312 KB/s（3.81x） | 482 KB/s（**5.89x**） |

单连接慢的根因不在带宽，而在 GitHub 对单个连接的吞吐限制与跨境链路的稳定性。同时另有真机反馈：**部分地区直连根本跑不通**，必须换源。

约束有三个：v1 已经交付了断点续传与通知栏进度，**这些行为一个都不能退化**；判定逻辑必须能在没有 Robolectric 的 JUnit 里直接跑（见 [CONTRIBUTING](../../CONTRIBUTING.md#3-运行单元测试windows-中文路径绕坑)）；镜像源是第三方，内容可信度必须能验证。

## Decision

**把单连接顺序下载升级为「8 路并发分片 + 仅在直连失效时启用的镜像源链」，并保留单连接路径作为降级退路。**

1. **并发数与调度**：固定 8 路 worker，抢一个共享的分片队列；分片切片固定 4 MiB、末片取短。`ApkDownloader.kt` 用一个 `RandomAccessFile("rw")` 随机写入，`completedChunks` 是完成度的**唯一权威**来源。
2. **降级判据**：服务端对 Range 请求返回 **200 而非 206** 时，整条下载退回 v1 的单连接顺序路径；500 / IO 异常**不**触发降级（那属于瞬时故障，重试即可）。
3. **镜像源链**：候选按「直连优先」构造；**Release 没有 `digest`（`sha256:...`）时强制禁用全部镜像**——因为镜像内容无法被校验。多个候选之间用 1KB Range 探测按实测延迟排序（`DownloadSourceSet.orderByProbe`）。
4. **开关默认值**：设计初稿定为「镜像加速默认关闭」，**2026-10-17 依据真机反馈（直连不可用）改为默认开启**；同时失败后提供「浏览器下载」弹窗作为最后的兜底。
5. **元数据兼容**：断点元数据 `.meta` 升级到 v2 以记录分片完成位图，`UpdateStore` 保留 v1→v2 的兼容解析；「清理缓存」清空分片但不删元数据（否则会丢掉续传能力）。
6. **纯逻辑下沉**：分片规划、进度聚合、Range 支撑判据、续传点判定、源链候选构造与校验全部放进不依赖 Android API 的文件（`ResumableDownload.kt`、`DownloadSourceSet.kt`），可直接单测。

## Consequences

正面：

- 实测吞吐从 82 KB/s 提升到 482 KB/s（**5.89x**），把"下载一个 APK 要等十几分钟"变成可接受的操作。
- 断点续传粒度从"整个文件"细化到"分片"，断网/切网/杀进程后的续传更稳；`completedChunks` 作为单一权威避免了进度回退。
- 镜像让"直连彻底不可用"的地区仍能完成更新，而 SHA-256 校验保证了镜像内容即便被篡改也装不上。
- 全部判定可单测，热路径 bug 能在 JVM 上复现（历史提交里这一模块的每次改动都带"纯逻辑 + 单测"标注）。

代价与风险：

- **对源站的压力更大**：8 路并发容易被 CDN 限流；这也是保留"降级到单连接"路径的现实原因。
- **镜像可控性差**：镜像的可用性与内容都不由本项目掌握，只能靠 digest 与探测排序降低风险；对没有 digest 的旧 Release 只能整体禁用镜像。
- **实现复杂度显著上升**：多了一个元数据版本（`.meta` v1/v2 双读）、一套降级判据、一个源链探测流程，出了 bug 的排查面变大。
- 需要用户侧网络配合：并发分片对某些代理/企业网络不友好，失败时要能优雅退回。

## 备选方案

1. **保持 v1 的单连接下载**：否，实测 82 KB/s，用户体验不可接受。该路径作为降级保留，但不再作为主路径。
2. **只上 4 路并发**：否，实测只有 3.81x，与 8 路的 5.89x 差距明显，而并发管理的复杂度几乎相同。
3. **上 16/32 路更高并发**：否。收益递减，且更容易触发源站限流；实测数据也只支持到 8 路。
4. **只加镜像、不做分片**：否。主收益来自并发（单连接 → 4 并发就有 3.81x），镜像只解决"直连跑不通"的可用性问题，两者不是替代关系。
5. **引入第三方下载库（OkDownload / FileDownloader 等）**：否。这些库自带的状态机与通知模型会和项目已有的"状态唯一权威 + 前台服务通知 + 自定义 `.meta` 断点"深度冲突，反而更难保证断点语义；自研纯逻辑部分可完全单测。
6. **改用 BT / 多镜像 P2P 分发**：否。客户端复杂度与合规风险都远超一个 APK 下载所需。
