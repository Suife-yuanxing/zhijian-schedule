## 1. 要解决的问题

课表页底部加号点下去后：加号原样不动、整屏以圆形扩散切进课程编辑页。四条诉求：

1. 点「+」后加号**顺时针转一定角度变成「×」**；
2. 展开动画曲线改为**由慢到快**，具体数值自行定制；
3. 返回动画采用**相通的设计**（同一套曲线的反向）；
4. 探索点**空课块**打开添加课程时的跳转 / 切换 / 返回交互。

### 1.1 第二版追加（同日，真机验证后）

第一版交付后用户提出两点，改变了扩散的**形状口径**与**方块的生命周期**：

5. 页面要**沿着整个加号方块展开（精准测量边缘）**——不是从方块中心长一个圆，
   而是边界起手就是方块本身；
6. 方块要**撑到页面完整展开之后**再离场，且**与页面展开同时**缩小（第二版末修订：
   最初实现为串行，真机看下来读成两次动作，改回同时）。

这两条推翻了第一版的核心结构（见 §2 的失效说明），因此 §2 / §6 的结论在第二版里
被替换，§3 的曲线结论继续有效（曲线只描述「边界走多快」，与边界是什么形状无关）。

## 2. 核心发现：为什么「先转 45° 再扩散」（**第二版已失效，见 §8**）

这一条决定了第一版的整个实现结构，必须先说清楚。第二版把方块搬到了裁剪层之上，
「必须等形变播完」这个前提随之消失——§2 保留为历史推导，现行结构见 §8。

扩散的几何是这样的：圆心 = 被点控件中心，**起始半径 = 被点控件半径**
（`RevealState.requestNavigation` 里 `startRadius = min(w, h) / 2`）。而 `RevealHost` 是把
新页面按圆裁剪盖上来、圆外铺旧帧。于是**正向起播的第 0 帧，圆内已经是新页面像素**：
加号在扩散开始的那一刻就被整块替换掉了。

结论：如果「转」和「扩散」同时开始，用户永远看不到那个 × ——转与不转屏幕上没有区别。
必须让形变先播完（或播到「读作转完」），再放扩散过去。

这解释了四个参数的全部取值：

| 参数 | 值 | 为什么是这个值 |
| --- | --- | --- |
| `Motion.FAB_MORPH_DEGREES` | 45° | 加号两条正交笔画绕中心转 45° **就是** ×；不需要第二套图标，也就没有 Add→Close 交叉淡入「两种字形光学重量不一致、中途糊一下」的问题。MUI `SpeedDialIcon` 同样用 `rotate(45deg)` |
| `Motion.DUR_FAB_MORPH` | 170ms | 一次点击的即时应答，不是转场。NN/g 把高频交互反馈定在 100~200ms。更长会整体推迟页面开始张开 |
| `Motion.FAB_REVEAL_HANDOFF_MS` | 150ms | `EaseOut` 前段极快，150ms 时已到 43.9°/45°，肉眼读作「已经是 ×」；剩 1.1° 在扩散遮住的头几帧里补完。取 150 而非 170，把「按下 → 页面开始张开」压在 150ms 内 |
| 缓动 | `Motion.EaseOut` | 转角是状态切换不是「被拿起」；回弹会让 × 抖一下，而 × 紧接着被圆吞掉，抖动只读作掉帧 |

**转回来**：从编辑页返回时按钮要重新是加号。不复位成「重新长出来」——用户离开时它已经是 ×，
回来看到的应该是它自己转回去。因此 `FabMorph.progressOf` 接住当前角度继续转，
而不是一律从 45° 起（动画被打断时它可能停在半路）。

## 3. 「由慢到快」的曲线选型

### 3.1 换算关系

扩散的里程碑要写成**行程比例**而非时间。设曲线反函数 `x(y)`，
半径走到 y* 的时刻是 `t = DUR × x(y*)`。保同一落点必须 `DUR_new = T* / x_new(y*)`。

本仓库沿用 `y* = 0.779`（半径 77.9%，Motion.kt 里有「画面读作已铺满」的口径）。

### 3.2 候选对比（数值解，非实测）

| 曲线 | x(y=0.779) | 保持 377ms 落点所需时长 | 25/50/75 行程 | 末端/起步速比 |
| --- | --- | --- | --- | --- |
| (0.3,0,1,1) 旧版 | 0.8369 | 450（自洽） | .130/.372/.668 | 4.99× |
| **（0.5,0,1,1）新版** | **0.8755** | **430** | **.075/.278/.586** | **14.10×** |
| (0.6,0,1,1) | 0.892 | 423 | .058/.234/.537 | 20.6× |
| (0.2,0,0.85,1) | 0.7513 | 502 | .188/.477/.777 | 0.69× |

两条硬结论：

1. **曲线越前重，收尾越不咬人**。末段斜率从 1.37 掉到 0.69 时，「末端一口气铺满最远角」
   这条设计 ID 就失效了。想要「由慢到快」，方向只能是 x1 变大。
2. **想更快只有一个旋钮：压时长**。所以曲线收紧后时长必须**往下补**，
   而不是像旧版那样往上加。

### 3.3 定案

```kotlin
val EaseRevealAccelerate = CubicBezierEasing(0.5f, 0f, 1f, 1f)
val EaseRevealDecelerate = CubicBezierEasing(0f, 0f, 0.5f, 1f)   // 严格时间镜像
const val DUR_REVEAL      = 400
const val DUR_REVEAL_BACK = 340
const val DUR_REVEAL_THEME = 450   // 换皮肤不跟页面转场一起动，见 §3.5
```

**为什么不是 (0.6,0,1,1)**：再往前就进「点了没反应」的区间——首 100ms 只走 3~4% 半径，
屏幕上几乎只有加号自己在转。0.5 是拐点：100ms 已铺开约 5% 屏幕面积，眼睛读得到
「东西长出来了」，同时末段仍有 14 倍速比。

### 3.4 感知换算（1080×2376、加号 24dp、起点半径 72px）

| 时刻 | 旧（.3@450）半径 / 屏幕覆盖 | 新（.5@400） |
| --- | --- | --- |
| 100ms | 10.6% / 8.3% | **6.9% / 5.0%** |
| 150ms | 20.2% / 19.2% | **14.8% / 13.0%** |
| 200ms | 31.2% / 33.2% | **25.4% / 25.4%** |
| 覆盖 50% | 245ms | **250ms** |
| 覆盖 90% | 391ms | **360ms** |
| 覆盖 99% | 429ms | **386ms** |
| 读作铺满（77.9%） | 377ms | **350ms** |

前段更静、后段更快，而总时长还短了 50ms——这正是「由慢到快」的观感来源。

### 3.5 反向为什么要「相通」而不是「更快」

`mirror(t) == 1 - accelerate(1 - t)` 这条恒等式有单测逐点钉住（1001 个采样点误差 < 1e-15）。
正向把 62% 的运动量压在最后 25% 时间里，镜像就把同样 62% 摊在开头：

| 时间点 | 旧反向 (0,0,.7,1) | 新反向 (0,0,.5,1) |
| --- | --- | --- |
| 10% | 13.74% | **18.02%** |
| 50% | 62.80% | **72.19%** |
| 90% 回收 | 291ms (@370) | **241ms (@340)** |

尾段淡出窗（`reverseMaskAlpha` 只在进度 0.9→1 化掉）：新曲线占 `(1 - 0.7101) × 340 ≈ 99ms`，
仍落在单测要求的 40~120ms 内——够「圆落到控件上不留硬边」，又不拖成一次独立淡出。

## 4. 空课块 / 空状态卡 / 加号：三个入口一条规则

原先只有加号走圆形扩散，空课块与空状态卡片的「添加课程」走横滑 push。三个入口进的是
**同一个页面**，两种转场是设计系统层面的不一致。本次统一成一条规则：

> **从被点的那个控件长出来。**

### 4.1 几何采集

`WeekGridBands` 里每个天列原本只有 `detectTapGestures` 的局部 offset。加了列框的
`onGloballyPositioned` 之后，由 `EmptyCellGeometry.cellOrColumn(column, sectionHeightPx,
localIndex, sectionCount)` 把「列框 + 段内下标 + 节高」折成格子矩形（纯逻辑，有单测）。

退化路径：列框还没测出来时给 `Rect.Zero`，调用方据此**跳过扩散直接导航**——
从 0×0 的圆起手等于整屏瞬切，比没有动画更糟。

### 4.2 返回目标

`AppNavHostState.fabOrigin` 的语义从「加号的位置」扩展成「上一个入口的位置」。
它**不能**再假设自己一定在右下角：返回目标可能是课表正中间某一格。

按一次返回时，旧页面按圆收进**当初被点的那个控件**，圆外露出实时课表。
这是正向的严格倒放，不是另写一套。

## 5. 两条与动效无关但必须一起做的修正

### 5.1 扩散从未接过 reduce-motion

全仓有 13 处读 `rememberAnimationsDisabled()`，而 `RevealHost` / `RevealState` /
`RevealMath` / `ScheduleFab` 一处都没有。用户在系统里关掉动画后，点加号仍会播 400ms
整屏擦除。本次补齐：

- `RevealDriver`：关动画时直接把 `progress` 写 1f（不是跑 0ms tween——0ms 仍会走一帧调度，
  而这一步的语义是「没有动画」）；
- `ScheduleFab`：关动画时跳过形变与等待，按下即走。

### 5.2 素墨主题的「墨不会跳」

`docs/specs/2026-10-29-三套主题重构设计.md` §3.6 写死「**不做**：缩放、弹性、旋转。墨不会跳。」
而 `ThemePreset` 当时没有 motion 字段，做不到按主题分流。本次新增：

```kotlin
enum class MotionProfile { Lively, Still }
// ThemePreset.motion，默认 Lively；素墨 = Still
```

只影响**装饰性**运动（旋转、回弹这类性格动作），不影响功能性转场：页面该从哪长出来、
圆该不该铺满，那是空间语义，任何皮肤都必须一致——否则同一个点击在不同皮肤下会跳到不同的地方。

因此素墨下加号不变形、扩散照常播：少一次形变只是少一次性格展示，跳页本身不受影响。

## 6. 可观测性：为什么这个 × 现在看得见

第一版是靠**串行**换来的可见性（形变先播、150ms 后才放扩散），代价是「按下 → 页面
开始张开」多等约 150ms。第二版把方块搬到裁剪层之上以后，这个代价直接消失了：

```
第一版：按下 ─170ms 形变─▶ 45° ─（≥150ms 等待）─▶ 扩散起播，方块随即被圆吞掉
第二版：按下 ─┬─ 170ms 形变（方块可见，无人遮挡）
              └─ 0ms 起扩散（边界从方块轮廓外扩）
        └─ 两条同时跑，方块一直看得见，直到被自己那次缩小吃掉
```

于是 `Motion.FAB_REVEAL_HANDOFF_MS` 与 `FabMorph.handoffWaitMillis` 都被删除：
它们的**存在理由**（方块会被盖掉）不再成立，留着只会让每次点击多等一次动画。
删掉的是判定，不是动画——转 45° 那一段照旧播。

## 7. 未验证项（据实标注）

- **未做逐帧数值对齐验证**：§3.4 的 ms / px / 面积表来自对 cubic-bezier 的反解与
  对圆/屏幕矩形的面积数值积分，不是实测帧数据；§8.6 的真机验证是**观感确认**
  （轮廓是圆角矩形而非圆、方块与展开同时动、铺满时方块已消失），不是逐帧时间戳对齐。
- **未验证低端机取帧耗时对 400ms 预算的挤压**：`RevealHost` 的取帧超时是
  `withTimeoutOrNull(400)`，与新时长同量级。若某机型取帧常态接近百毫秒，
  实际可见时长会被再削，可能出现「开头直接跳 1/4 轮廓」。
- **未验证方块副本在极端缩放下的抗锯齿**：`SeedOverlay` 用 `Canvas` 手绘圆角矩形 +
  两条笔画，而不是复用 M3 `Icon`。低端机在 1~2px 尺寸段可能比矢量图标更早出现锯齿。
- **未验证 10x 慢放以外的帧率分布**：本轮验证统一在 `animator_duration_scale = 10` 下
  拍摄（每帧约 42ms 真实时间），60Hz/120Hz 下的实际观感未单独采样。

## 8. 第二版：轮廓种子 + 同时离场

### 8.1 形状口径：从「圆」改成「种子的等距膨胀」

边界不再是圆心 + 半径，而是**被点控件实测轮廓的 Minkowski 和**：

```kotlin
data class SeedShape(val bounds: Rect, val cornerRadius: Float, val badge: SeedBadge? = null)
```

外扩 g 之后的轮廓 = 矩形四边各向外 g、圆角半径同步 +g。覆盖整屏的最小 g：

```
g = max(left, width - right, top, height - bottom) + 2
```

（+2 是抗锯齿留边，否则最后一帧屏幕边缘会留一条 1px 的旧页线。）

为什么不用对角线长度（圆的口径）：方块贴右下角时，对角线会把上边与左边各推开一大截，
起手那几十毫秒里方块外会先露出一圈多余的新页面——**正是本次要修的病灶**。
改成轮廓口径之后，「边界始终是方块自己的等距外扩」是构造出来的性质，不是调出来的参数。

圆角半径必须随外扩同步增长：不增长的话形状会从「圆角方块」→「方角方块」→「圆」，
眼睛读得到「形状变了」，而不是「它长大了」。

**外扩为 0 时轮廓就是方块本身**——这是「页面从方块里长出来」的几何定义，也是单测里
`zeroDilationEqualsTheWidgetItself` 钉住的那条。

换主题仍是圆（`RevealShape.Circle`）：皮肤之间从胶囊长出一个圆是既有语义，本次不动。
两套口径并存是刻意的，不是没统一——`RevealShape` 是 sealed interface，形状是编译期契约。

### 8.2 方块为什么要搬到浮层

第一版方块活在课表页里，导航一发生它就被销毁，所以只能靠「先转完再放扩散」抢 150ms。
第二版要求它撑到页面铺满之后，于是它被搬到 `RevealHost` 的 `SeedOverlay`：
按同一份实测几何（`SeedShape` + `SeedBadge`）重画一枚盖在裁剪层**之上**。

副作用与处理：

- **必须在裁剪层之上**：否则它和第一版一样被新页面盖掉；
- **必须与真按钮同帧重合**：副本只在「按下那一帧」与「缩到 0 那一刻」与真按钮重合，
  中间所有帧真按钮都已离开组合，所以接缝不可见；
- **只有正向要副本**：返回时真按钮还在课表页里活着，画副本会变成两个方块；
- **金属主题**：`SeedBadge.highlight` 非空时补一团球冠高光，比例由 `seedHighlight()` 给出。

### 8.3 编排：同时离场（第二版末修订）

中间版本是串行（页面先铺满 400ms，再缩方块 240ms，总长 640ms）。真机 10x 慢放逐帧看下来，
那段串行读成「动画播完了，然后方块又动了一下」——**两次动作**。于是改成同时：

```kotlin
animate(0f → 1f, tween(DUR_REVEAL, EaseRevealAccelerate)) { value, _ ->
    state.progress.floatValue = value    // 轮廓外扩
    state.seedExit.floatValue = value    // 方块离场（同一个 value）
}
```

为什么写在**同一个帧回调**里，而不是两条各跑各的协程：两条协程只能靠时长凑齐，
一旦系统动画缩放、掉帧或连点打断，两者就会各自漂移，方块的缩小会与轮廓的铺满错开成
两次动作。写成一个 value 写两个槽，逐帧对齐是**构造出来的性质**，不依赖调参。

因此 `SeedMotion` **没有** `durationMillis` 字段：给不出、也不该给出独立时长。

### 8.4 方块离场的感知参数（**第三版已整体替换，见 §8.7**）

> 下表是第二版末的参数。第三版把「缩放」这一整条换成了「内缩 + 圆形化」，
> 理由见 §8.7.1；本表保留用于对照，**不要按它实现**。

| 参数 | 第二版值 | 第三版 |
| --- | --- | --- |
| 形状变换 | 缩放 1 → 0（相似变换） | 四边等速内缩 + 圆角朝半边化（与边界同族） |
| 锚点 | 方块中心 | 方块中心（内缩天然居中） |
| 淡出窗口 | 0.6 → 1 | 本体 0.18 → 0.62；字形 0.24 → 0.40 |
| 颜色 | 无 | 边界 2dp 橙色描边 1 → 0.5 行程 |
| 可见阈值 | alpha ≤ 1% 即不画 | 同 |

### 8.5 素墨（`MotionProfile.Still`）

方块不转、不缩，只淡出；扩散边界仍从方块轮廓外扩。
理由同 §5.2：**空间语义不因皮肤而变**，被砍掉的只是装饰（旋转、缩放）。

### 8.6 真机验证（2026-11-04，10x animator scale，PKG110）

已验：轮廓从方块外扩（边界是圆角矩形而非圆）、方块与展开同时缩小、铺满时方块已消失、
返回时边界反向收回且不出现第二个方块。证据帧：`.tmp/s4/04..12.png`、`.tmp/r4/03..06.png`。

### 8.7 第三版：退场不是「缩小」，是「被吃掉」（2026-11-05）

#### 8.7.1 为什么第二版的退场读错了

用户在真机上给出的判断是：方块读作「一个小方块在白色页面上缩小然后淡掉」，
和「页面从方块里长出来」不是同一套语言。根因不在时序、不在缓动，而在**算子的族**：

| | 页面边界（扩张） | 方块退场（第二版） |
| --- | --- | --- |
| 算子 | 闵可夫斯基外扩（四边平移 +d、圆角 +d） | 相似变换（按比例内移到中心） |
| 形状比 `r / side` | 随 d 单调升，趋近 1/2（正圆） | **恒定不变** |
| 与对方的关系 | — | 只在 p = 0 这一帧重合 |

也就是说：边界越胀越圆，方块越缩越「方」。两条曲线只在第 0 帧相交，之后分道扬镳。
**任何缓动函数都调不到同族**——这不是时间问题，是几何问题。第二版把 `seedScale` 写成
`1 - p` 的线性映射，无论把 `EaseRevealAccelerate` 换成哪条曲线，方块的形状比都不会动。

#### 8.7.2 为什么不能用「外扩的逆」

严格的逆运算是**腐蚀**（四边等速内移）。但两条行程的尺度差了 26 倍：
外扩要走 `dilationToCover = 1898px` 才盖满，而方块短边只有 144px、可用内移上限 72px。
按扩张的同一条速率倒放，方块会在 `p = 72 / 1898 ≈ 0.038`（约 15ms）被吃干净——
等于按下去就消失，连「被吃掉」的过程都没有。

所以退场不能是扩张的逆，只能是**在同一个形状族里朝同一个吸引子走**。

#### 8.7.3 定案：两头都朝「圆」去

扩张让形状比从 1/3 走到 1/2；退场就让方块**也**从 1/3 走到 1/2，只是同时四边内缩。
任一帧上，边界与方块是同一族曲线上朝相反方向走的两点——这就是「同一套语言」的可执行定义。

```kotlin
internal fun shrunkenRound(seed, progress, roundOut): RoundRect
// 内缩：inset = min(w, h) * 0.25 * smoothstep(0.06, 0.44, p)   四边各退这么多
// 圆角：lerp(r0, limit, smoothstep(0, 0.32, p))                limit = 内缩后短边的一半
// p = 0 时与 dilatedRound(seed, 0f) 逐字段相等 —— 接缝不跳
```

`p = 1` 时是正圆、边长收到一半（72px），但那时 alpha 早已归零，看不到这一帧；
它的作用是把整段退场的**方向**定死，而不是被看见。

#### 8.7.4 三层的先后顺序：借 `fadeMode` 的两条语义

Material 的 `MaterialContainerTransform` 有四个 `fadeMode`（官方定义，见 SDK 参考）：

| 常量 | 值 | 官方语义 |
| --- | --- | --- |
| `FADE_MODE_IN` | 0 | 只淡入入场内容，出场内容的不透明度**不变** |
| `FADE_MODE_OUT` | 1 | 只淡出出场内容，入场内容的不透明度**不变** |
| `FADE_MODE_CROSS` | 2 | 出场与入场交叉淡化 |
| `FADE_MODE_THROUGH` | 3 | 先淡出出场内容，**再**淡入入场内容（有先后） |

本项目只借用其中两条，不是整体照搬：

- **`OUT` 的那半句**（「入场内容不动」）——新页面从第 0 帧起就是不透明的新内容，它的
  出现完全由裁剪边界负责，全程没有任何淡入。这一条已经由 §8.1 的轮廓裁剪满足了。
- **`THROUGH` 的先后**——出场的那一侧（方块）内部还有两层：内容（字形）与容器（本体）。
  `THROUGH` 的「先走一个、再走另一个」正是这里要的顺序，只是**不走入场那一半**。

换句话说：**容器侧用 `THROUGH` 的时序，入场侧用 `OUT` 的语义**。两者不冲突，因为
入场侧根本没有「容器内的内容」——页面不是从方块里淡进来的，是被边界揭示出来的。

| 层 | 窗口（进度） | 对应时刻 | 为什么在这个窗口 |
| --- | --- | --- | --- |
| 字形（+ → ×） | 0.24 → 0.40 | 186 → 240ms | 转 45° 要 170ms，必须在满不透明下走完，否则那个 × 是半透明地出现又消失，等于白转 |
| 方块本体 | 0.18 → 0.62 | 167 → 304ms | 起点晚于字形开始之前一点点（本体先立住），终点落在页面还在明显扩张时（0.62 时外扩 1177px ≈ 8 个方块宽） |
| 边界描边 | 0 → 0.5 | 0 → 275ms | 颜色移交，见 §8.7.5 |

顺序反过来（方块先化、× 还挂着）会读作「一个 × 浮在页面上」，比「一个方块浮在页面上」更糟。

#### 8.7.5 颜色移交：方块的颜色变成页面的边

形状只说明「同族」，说明不了「就是它变的」。第二版里方块一化掉橙色就凭空消失，
页面从浅底开始是它自己的底色——读作两个无关的东西前后出现。

第三版在 `SeedOverlay` 里**先画**一条 2dp 的橙色描边，路径就是当帧的 `boundaryPath`：

- 第 0 帧描边与方块轮廓完全重合，且被方块本体盖住，看不见；
- 边界一旦离开方块，橙色就以一条细边独自向外跑（1 → 0.5 行程，`smoothstep`）；
- 2dp 是「看得出是线、又不像给页面镶框」的分界：1dp 在加速末段会被运动模糊吃掉，
  3dp 以上读成独立装饰边框而不是「从方块里被拉出来的一道边」。

这是全篇唯一的颜色传递路径，不额外引入任何视觉元素。

#### 8.7.6 仍然满足「同时离场」

三层全部读同一个 `RevealState.seedExit`，而 `seedExit` 与 `progress` 仍写在**同一个
`animate` 帧回调**里（§8.3 的结构没动）。形状变了、层数多了，但时间线只有一条。

#### 8.7.7 素墨

`SeedMotion.roundOut = false`：不圆、不缩、不加描边，轮廓原样，只靠 `seedAlpha` 离场。
「不转不缩」是主题身份而不是无障碍降级（§8.5），所以这条不能被几何改动牵动。

#### 8.7.8 与业界做法的对照

Material 的 container transform（`MaterialContainerTransform` / Flutter `OpenContainer`）
与 Compose 的 `SharedTransitionLayout` 都建立在**共享容器**上：一个容器从起点 bounds
插值到终点 bounds，内容在里面交叉淡入淡出。它们的公式是「**一个**容器 + 内容换班」。

本项目没有共享容器——导航把课表页和编辑页彻底换掉，两页之间没有任何共同的 Composable。
所以形状连续性只能靠**几何重画**来伪造：浮层按实测轮廓重画方块，边界按同一份几何公式外扩。
这也是为什么「同族」这件事必须写在算子层：没有共享容器可依赖，唯一的黏合剂就是两条曲线
在数学上属于同一族（矩形 + 平移膨胀 + 圆角同步）。

第三版的出场顺序借的是 `fadeMode = THROUGH` 的**先后语义**（不是 `CROSS` 的同时）：
容器（方块本体）在字形之后才走完，读作「它先失去内容，再被吃掉」。
入场侧则用 `OUT` 的语义——新页面全程不淡入，只被边界揭示。详见 §8.7.4。

#### 8.7.9 真机验证（2026-11-05，PKG110 / 3B6F6DE7EB6P9WV5，debug 包）

`screencap` 单张约 400ms，60fps 下要 11ms 一帧，连拍必然漏帧。于是把 `animator_duration_scale`
提到 20（400ms → 8s），漏帧密度降到可接受；再用设备端 `date +%s%N` 给每张图打墙钟时间戳，
反算真实进度。20 张连拍覆盖整段。

**先确认时钟确实生效**：用 7 个「已量出进度」的帧做最小二乘拟合，得 `D = 8036ms`、
`t0 = -109ms`，残差全部 ≤ 0.002（进度单位）。理论 400 × 20 = 8000ms ⇒ 实际缩放 20.09×。
拟合优度这么好，说明 ①`TweenSpec` 确实每帧被调用了 ②时间戳可靠 ③后面的形状测量可信。

#### 8.7.10 本轮发现并修掉的一个真 bug：探针泄漏 + 统计被清零

`SeedFrameProbe` 在设备上暴露了两个问题，都不是观感问题，是它自己的生命周期错了：

1. **`stop()` 只写在正常路径上**。`animationsDisabled` 分支是提前 `return@LaunchedEffect` 的，
   那一支永远不会调 `stop()`，Choreographer 回调永不注销。实测泄漏出 **3289 帧、54 秒**的采样，
   而这一支恰恰是「不要动画」时最该零开销的路径。修法：把 `stop()` 挪进 `finally`。
2. **`watch()` 直接写在组合体里**。它每次被调用都新建一个 `SeedFrameTimeline` 当本轮统计，
   而动画期间组合体每帧都可能因别的状态变化重进——日志里那些重复的 `frame=1`、`frame=2`
   就是这么来的（同一轮出现过三段）。修法：包进 `LaunchedEffect(active.runId)`，一轮只挂一次。

修完复验：1x 下一次点击恰好 1 条 `summary`、1 条 `frame=1`；scale=0 下同样 1 条 `summary`，
`samples=0`（驱动直接写 1f，压根没有时间线）。

#### 8.7.11 真机采样暴露的掉帧（**未修，属既有问题**）

`SeedFrameTimeline.maxGapMs` 在 1x 下给出 177~288ms 的单次间隔，而中位间隔是 11.1ms（90Hz）。
位置固定在**进度 0.01~0.34 之间**，也就是旧帧整屏位图正在铺底的那一段。三次重复点击均复现，
不是冷启动一次性。

这一条与第三版的形状改动无关（第二版同样的采样代码没跑过，无法对比），且它落在
「方块刚开始内缩」的窗口里，会把最关键的起手段吃掉一两帧。本轮没有动渲染层去治它，
只把事实记下来——要继续查，下一步是 `dumpsys gfxinfo` 看那一段的帧耗时构成。
